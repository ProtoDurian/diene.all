# Updating this project from its CyanPrint template

This repository was generated by a CyanPrint template, and that template is built on parent
templates. `.cyan_state.yaml` records the template, its version, your answers and every merge
decision. `cyanprint update` uses it to pull template changes into this repo.

## How it works (so the steps make sense)

- **Base:** CyanPrint regenerates the template at the version recorded in `.cyan_state.yaml`,
  using your recorded answers.
- **Theirs:** it generates the newest published version, reusing your answers. Only new questions
  are asked.
- **Ours:** every file on disk, including untracked and git-ignored ones.
- These three meet in a real `git merge` with rename detection. Changes on one side only merge
  cleanly. Lines both sides changed are left in the file as standard `<<<<<<<` markers.
- A parent template's fix reaches this repo only after the template **above this repo** has been
  republished. If `update` reports `updated templates: none`, there is nothing new. Ask whoever
  publishes the templates; do not hand-copy the change in.

## Steps

1. **Commit first.** Run `git status`; it must be clean. CyanPrint does not check this. A clean tree
   makes `git diff` show exactly what the template changed, and `git checkout -- . && git clean -fd`
   undoes a bad update.
2. **Remove installed dependency directories** such as `node_modules/`. CyanPrint 4.9.2 reads every
   file on disk and refuses to write through hard links, failing with
   `Refusing to write through a hard link inside the project: node_modules/...`. `bun install`
   creates hard links on Linux. Delete the directory; you reinstall it in step 5. (Drop this step
   once the fixed CyanPrint is in use.)
3. **Update:**
   - `cyanprint update .` — newest version of every installed template;
   - `cyanprint update . --template owner/name` — one template only;
   - `cyanprint update . --template owner/name@N` — a specific version;
   - in CI or headless runs, add `--headless --answers answers.json` for any new question.
4. **If it exits non-zero with `merge_conflicts_pending`:**
   - The listed files contain `<<<<<<<` / `=======` / `>>>>>>>` markers. Nothing else ran:
     post-generation commands were skipped and `.cyan_state.yaml` still points at the old version.
   - For each conflicted hunk, **keep the incoming (template) side** for now. Then re-run the same
     `cyanprint update .` command. The re-run merges from the old version again, so a hunk you
     resolved any other way conflicts again.
   - When it reports `updated`, re-apply any local change you still need, as a separate commit on
     top.
   - Check that no markers are left: `git grep -n -e '^<<<<<<< ' -e '^>>>>>>> '` must print
     nothing.
5. **Reinstall and run CI locally:** reinstall dependencies (e.g. `bun install`), then run the
   repo's normal gates (`pre-commit run --all-files`, the test suite, and any probes the repo
   carries). Fix what breaks in your own code, not in template-owned files, unless you mean to
   diverge from the template.
6. **Commit** the update and the new `.cyan_state.yaml` together, e.g.
   `chore: cyanprint update owner/name 7 -> 8`, then open a pull request.

## Rules

- **Never edit `.cyan_state.yaml` by hand.** It is the merge base for every later update. A hand
  edit makes the next update merge against a template output that never existed.
- **Never delete `.cyan_state.yaml`.** Without it, `update` cannot run at all.
- **Do not commit with conflict markers in files.**
- **Do not hand-copy template changes.** If a fix is missing, the template above this repo needs
  republishing. Tell its owner.
- **Template-owned files:** prefer changing them in the template rather than here. Every local edit
  to a template-owned line is a future conflict.
- **Installed from a local path?** If `.cyan_state.yaml` shows a local `source:` (a filesystem path,
  `version: local`), `update` re-reads that same path as its base. It never sees changes. Re-install
  from the registry to receive updates.
- **Do not run `cyanprint create` into this directory to "refresh" it.** That adds or re-adds a
  template install (a different flow). Use `update`.
